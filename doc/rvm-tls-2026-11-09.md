# NetBSD/RVM emulated TLS — 2026-11-09

The static bootstrap runtime now supports initialized and zero-filled C
`__thread` and C11 `_Thread_local` objects in its single-LWP execution model.
The compiler already emits calls to `__emutls_get_address`; the missing
runtime implementation is now built from the tree's GCC libgcc source.

## Compiler/runtime ABI

GCC describes each TLS object with a 32-byte control object: eight-byte size,
alignment, cached location and initial-template pointer fields. Descriptors
are ordinary writable FHR data; nonzero initial values are copied from
relocated templates. Objects are allocated on first access and retain their
addresses until process exit. Explicit alignment, including 64 KiB alignment,
does not require large-alignment support from ordinary malloc.

`stand/user/emutls.py` builds
`external/gpl3/gcc/dist/libgcc/emutls.c` with ordinary C headers and the
nonthreaded gthread setting in place of GCC's generated configuration
headers. It retains the implementation and its GCC Runtime Library Exception
license notice. Both `__emutls_get_address` and `__emutls_register_common` are
included in `librvm.a`. The source is compiled with the same compiler and ABI
flags as the rest of the runtime instead of reusing an installed libgcc member.
Compile-time assertions check the word sizes, descriptor size and field offsets.
No compiler or emulator changes are required.

The existing FHR adapters preserve private descriptor/template symbols,
including file-local variables with the same name in separate translation
units. External TLS references resolve to the defining translation unit's
descriptor. Static initialization runs after the allocator/environment are
usable, so constructors can access TLS. Atexit handlers and destructors run
while its storage is still valid.

Fork inherits initialized TLS values and cached addresses through the normal
COW address space. Child writes and allocations for previously untouched TLS
objects do not change the parent. Exec creates fresh descriptors/templates and
runs the new program's constructors. Longjmp preserves ordinary TLS memory
updates; it does not roll them back. Signal handlers can access objects that
were allocated before signal delivery; first access that invokes malloc is
not async-signal-safe.

## LWP-private pointer

The runtime now exposes `_lwp_getprivate` and `_lwp_setprivate` through the
existing MI kernel syscalls. The pointer is opaque, independent of GCC's
emulated TLS storage, and retains all 64 bits, including values with the high
bit set. The get veneer must return the raw result rather than interpret a
negative-valued pointer as an errno. Fork inherits this pointer and the MI
exec path clears it.

This does not assign an RVM hardware TLS register or enable the ELF TLS
variant flags. `_UC_TLSBASE` remains unsupported by the MD context interface.
Pthreads, concurrent user LWPs accessing emulated TLS, dynamic TLS/DSOs,
nontrivial C++ thread-local destructors and full libc/csu integration remain
unported. The runtime and allocator remain single-threaded; the nonthreaded
emutls path must be replaced when that execution model changes.

## Guest validation

The disk fixture runs `/sbin/tls-check`. It exercises numeric, aggregate and
pointer templates, zero-filled data spanning a 64 KiB page boundary, over-aligned
storage, external and file-local TLS, function-local C11 TLS, stable addresses,
constructor/atexit/destructor access, signals, setjmp/longjmp, timed sleep,
fork/COW, child-only lazy allocation, exec reset and the LWP-private pointer.
The final success marker is emitted by a destructor after it has checked TLS
and confirmed that its atexit handler ran.

```sh
./build-diskroot.sh
python3 sys/arch/rvm/tests/hardfile.py --objdir obj.rvm-diskroot \
    --diskroot --expect-accel
python3 sys/arch/rvm/tests/tls.py
```

`tls.py` compiles and executes the fixtures at `-O0`, `-O2` and `-Os`, and
requires successful exit after the destructor marker. Its transcript is
`obj.rvm-diskroot/tls-64.log`; `--ram-mib 640` selects the larger memory size.
The normal boot/persistence transcripts remain under `hardfile-tests/`.

Validation passed the TLS fixtures at all three optimization levels, normal
and DIAGNOSTIC boot/persistence at 64/640 MiB, a 64 MiB software-float
boot/persistence run, and interactive shell/keyboard/keypad/pixel checks.
